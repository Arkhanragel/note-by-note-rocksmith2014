# Note-by-Note: technical notes

What Note-by-Note found out about Rocksmith 2014 Remastered and how the mod uses it. Written for other modders, especially the [RSMods](https://github.com/Lovrom8/RSMods) community, whose research this project built on. Everything here was checked on the running game.

- Game build: **Learn & Play** (Steam, December 2024 onwards, RSMods `LPDecember2024`), PE checksum `0x0176EC34`, link time `0x67497D00`, 24,514,584 bytes. The older Remastered build (Sept 2022, `0x00B13D7C`) is in testing, see [Game builds](#game-builds-and-where-addresses-live).
- All addresses are **RVAs** (add the exe's load address; the L&P exe uses ASLR). Offsets are hex bytes.
- 32-bit process. Nothing in the game's code is patched: the mod reads/writes data, calls existing functions, and hooks system DLLs (d3d9, ntdll, winmm) only.

## Architecture

```
Rocksmith2014.exe
 └─ RS_ASIO.dll (v0.7.5 + a small patch)
     ├─ copies the raw guitar input into shared memory on every ASIO buffer switch
     └─ loads NoteByNote.dll on a thread at start-up
         ├─ main loop (~1 ms): game state, guitar detection, wait logic        mod/nbn/main.cpp
         ├─ game access: build table, pattern search, readers, freeze          mod/nbn/game.cpp
         ├─ overlay: d3d9 Present/Reset hooks + Dear ImGui                     mod/nbn/overlay.cpp
         └─ NoteByNote.ini (settings), NoteByNote.log, NoteByNote_report.txt
```

The main loop and the render thread share one small state object behind a mutex: the loop sends *what to show* (a `View`: waiting note, tab notes, beats, song time), the menu sends back *settings* and skip requests.

## Game builds and where addresses live

Like RSMods' `VersioningStruct`, the build is picked by the exe's computed PE checksum (`MapFileAndCheckSumA`). Everything build-specific is one row of `kBuilds` in [game.cpp](../mod/nbn/game.cpp):

```cpp
struct Build {
    const char* name;
    DWORD checksum;   // computed PE checksum (same as RSMods)
    DWORD timestamp;  // PE link time: a copy patched on disk keeps this + the header CheckSum field
    bool verified;    // checked by hand on this build
    Addresses addr;   // RVAs of code and globals
    Layout layout;    // offsets inside the game's objects (song object, clock, DD, provider, menu chains)
};
```

Differences from RSMods' approach, in case they're useful:

- **Unknown exe = the mod stays off** (RSMods shows a MessageBox and falls back to Sept 2022 values). The log and report print the exe's numbers so a player can report them.
- **Patched on disk:** any byte patch changes the computed checksum. If the computed one doesn't match but the header CheckSum field and the link time match a known build, it's treated as that build, patched.
- **Pattern search** ([signatures.h](../mod/nbn/signatures.h), generated by [tools/sigmaker.py](../tools/sigmaker.py) from a memory dump): every address has 1-3 byte patterns (absolute addresses and rel32 targets wildcarded, grown until the only match in the executable sections is the target). On a build without a verified row the mod can find its addresses by itself (`TestUnverifiedGame=1`). On L&P all patterns give exactly the verified table.
- **Object offsets are per build too** (`Layout`), so if a report shows one moved on another build, the fix is one table entry.
- **The report** (`NoteByNote_report.txt`) lists the exe numbers, each address (pattern vs table), the layout in use, and checks made while playing: chart read, DD vector size == phrase-iteration count, clock moves ~1 s per s, freeze holds the clock (< 0.1 s drift), resume runs it again.

The Sept 2022 row currently holds RSMods' values (absolute there, exe base 0x400000) and is marked unverified; the provider vtable isn't known for it. Testers are being asked for reports, see the [README](../README.md#help-test-the-older-game-version).

## Object layouts

Chains: read the pointer, add the offset, repeat.

| Chain | Result |
|---|---|
| `[root] +0x28 → +0x8C → +0x0` | current screen name, e.g. `MainMenu`, `LearnASong_Game`, `LearnASong_RiffRepeater`, `LearnASong_Pause` |
| `[root] +0x28 → +0x8C` | before the first dialog the name is stored **in place** here (`MainOverlay`, `TitleScreen`); the chain above faults until then |
| `[previewName] +0xBC → +0x0` | `Play_<SongKey>_Preview` (only while the song list shows a song; `_Invalid` with previews off) |
| `[root] +0xB0` | the **song object** (while a song is loaded) |
| `[root] +0x68 → +0x10 → +0x2C → +0x28 → +0x3DC` | float: the **grey-out time**: every note before it is greyed out on the highway. After resuming from the pause screen the game goes back ~3 s and replays with the notes already passed greyed (RSMods `ptr_greyOutNoteTimer`; checked on L&P: paused at 136.43, resumed at 133.41, grey time stayed at the pause point). Note-by-Note doesn't wait for those notes again (setting `SkipGreyedNotes`); it only trusts a value up to 20 s ahead of the clock |
| grey-out float −0x1C / −0x18 / −0x14 (and −0x10) | **Riff Repeater's loop**: start, the grey time the game really uses there (back to the loop start each time the loop starts over, while the timer above keeps the pause point), end (twice). Outside Riff Repeater: 0, the grey time, the song's end, the song's end. At the loop end the game rewinds the highway over ~1.5 s (the clock goes down gradually). Note-by-Note waits only inside the loop and reads the grey time from −0x18 there (checked on L&P, 3 loops) |

**Song object** (`song`):

| Offset | What |
|---|---|
| `+0x78` | pointer to the loaded arrangement, **same layout as the SNG file** (below) |
| `+0x7C` | pointer to the Dynamic Difficulty state |
| `+0x3B4` | float: **the song clock**, seconds. The value ~14 game systems read (highway, scoring...) |
| `+0x538` | the "song timer" RSMods/RockSniffer read: a *copy* written from the clock (rva 0x3DDA80); writing it has no effect |

**Clock provider** (object with vtable `0xDA0E70`; not referenced from the song object, found by scanning committed private RW memory for `[p] == base+0xDA0E70 && [p+0x0C] == song`, under 1 ms):

| Offset | What |
|---|---|
| `+0x0C` | back pointer to the song object |
| `+0xCC` | Wwise **playing ID** of the music the clock follows |
| `+0xDA` | byte: **stopped** flag. While != 0 the clock doesn't advance |

**Dynamic Difficulty** (`dd = [song+0x7C]`): `+0x18` = vector of 64-byte entries, one per phrase iteration; `*(int*)(entry + 4)` = the level currently shown for that phrase iteration (negative = none). Found by putting hardware read breakpoints on notes of every level: only the shown level is read, by the note search at rva 0x3F1B40.

**Arrangement** (`data = [song+0x78]`, the SNG layout; vectors are begin/end/capacity, 12 bytes):

| Offset | What |
|---|---|
| `+0x34` | beats, 16 B: float time, int16 measure, int16 beat, int32 phrase iteration, int32 mask (bit 0x1 = first beat of a bar) |
| `+0x40` | levels, 0x64 B each, **in difficulty order** (Level+0x0 is not the difficulty) |
| `+0x58` | phrases, 44 B |
| `+0x64` | phrase iterations, 0x18 B: phrase id, start time, end time |
| `+0x94` | chord templates, 0x48 B: `+0x4` frets[6] (int8, -1 = not played), `+0xA` fingers[6], `+0x10` MIDI notes[6] (int32), `+0x28` name char[32] |
| `+0xAC` | chord notes |
| `+0x110` | tuning, vector<int16>: semitones per string vs E standard |
| `+0x11C` | capo, int8 (-1 = none) |
| `+0x148` | float song length, seconds |

**Level** `+0x30` = vector of notes, **0x1C8 bytes each in memory** (the file's notes are packed; field order is the same up to the sustain):

| Offset | What |
|---|---|
| `+0x00` | mask (0x2 = chord, 0x40000 = ignore / not scored) |
| `+0x0C` | float time |
| `+0x10` / `+0x11` | int8 string (0 = thickest) / int8 fret |
| `+0x14` | chord id (index into the chord templates) |
| `+0x20` | phrase iteration |
| `+0x3C` | float **sustain**, seconds (0x38 in the file layout is *not* it in memory) |

Validation: a chart rebuilt from memory ([tools/memchart.py](../tools/memchart.py)) was identical to the one exported from the song file with Rocksmith2014.NET (2054 lines, 6 levels, 36 phrase iterations). No bass/guitar flag was found; the chord templates' MIDI notes carry the bass offset (-12), which is used to tell them apart.

## The song clock

Traced from the disassembly of a memory dump:

```
Wwise GetSourcePlayPosition(playingId = provider+0xCC) / 1000        (rva 0x4C550)
  -> provider+0x174 (+0x178 = a smoothed copy)                         (rva 0x4BA80, 0x4CC70)
  -> song+0x3B4                        (via provider vtable+0x38, from the song update at rva 0x3DF250)
       read by the highway, scoring, ... (~14 systems)
  -> {1, 0, time, remaining} record = song+0x538 "timer"               (rva 0x3DDA80)  a copy
```

- The clock is driven by the audio position, not by frames: when rendering froze (the Windows F10 menu-bar key), the clock kept running.
- `provider+0xDA != 0` makes rva 0x4C550 return early: the clock stops.
- **The game's own pause** posts `Pause_TMusic` and `Stop_TMusic` on game object `0x1234` and sets `provider+0xDA = 1`. It *stops* the music and restarts it a few seconds earlier on resume (the ~7 s rewind players see).

## Pausing the song without a pause screen

The core of Note-by-Note. What works (music and highway stay in sync, no rewind):

```cpp
// freeze
uint32_t pid = *(uint32_t*)(provider + 0xCC);
uint32_t ev  = GetEventIDFromPlayingID(pid);                       // 0 = no music playing right now
ExecuteActionOnEvent(ev, /*Pause*/ 1, /*song game object*/ 0x1234, 0, /*linear*/ 4, pid);
*(uint8_t*)(provider + 0xDA) = 1;                                  // hold the clock

// resume
ExecuteActionOnEvent(ev, /*Resume*/ 2, 0x1234, 0, 4, pid);
*(uint8_t*)(provider + 0xDA) = 0;
```

Measured: frozen at 14.386 s, resumes from 14.434; frozen at 24.733, resumes from 24.872 (the clock's own smoothing). The report checks it on every run: the clock must move < 0.1 s while held and ~1 s in the first second after.

What didn't work, to save others the time:

- **Time_Stretch RTPC** (RSMods' speed control, with the actor-mixer effect attached): highway, music and clock slow down together, but the floor is **0.24x**; it can't stop a song.
- **Seek on resume** (`SeekOnEvent` to the frozen time): lands slightly off (the music segment time isn't the source position), so music and highway drift apart.
- **Muting the song's game object** while holding the clock: the function RSMods labels `SetGameObjectOutputBusVolume` (rva 0xAC0E10) had no audible effect.
- `ExecuteActionOnEvent("Play_<key>", Pause, AK_INVALID_GAME_OBJECT)` returns AK_Fail: the pause has to target the exact playing ID and the song's game object.

## Chart and Dynamic Difficulty from memory

The mod never reads song files at run time. When `[song+0x78]` changes it reads the whole arrangement (all levels, phrase iterations, chord templates, beats, tuning, capo, length) into its own structures ([game.cpp](../mod/nbn/game.cpp) `ReadSongChart`). Every 50 ms it reads the DD levels and, for each moment, uses the level shown for the current phrase iteration. That is what makes it follow Riff Repeater's level slider and DD changes: the note it waits for is the note on the highway.

## Guitar audio (RS_ASIO tap)

RS_ASIO owns the ASIO device, so nothing else can open it. Our RS_ASIO build is upstream **v0.7.5** plus [one patch](../mod/rs_asio_tap/rs_asio_v0.7.5_guitartap.patch): in the input branch of `RSAsioAudioClient::OnAsioBufferSwitch`, before RS_ASIO's software volume, input channel 0 is copied as float into a named file mapping. The same patch loads `NoteByNote.dll` on a thread from `DllMain`.

```cpp
// mod/common/GuitarTapShared.h
name  "Local\\NoteByNote_GuitarInput"
struct GuitarTapHeader {        // 64 bytes
    uint32_t magic;             // 'NBN1'
    uint32_t version, sampleRate, capacity;   // capacity = 65536 samples (1.37 s at 48 kHz)
    volatile int64_t writePos;  // total samples written, published with InterlockedExchange64
    uint32_t writerPid, blockFrames;
    volatile uint32_t lastWriteTick;
    uint32_t reserved[7];
};
float samples[65536];           // ring: sample i lives at samples[i % capacity]
```

Readers must map it **read + write** (a 64-bit atomic read is done with `InterlockedCompareExchange64`, which writes). The Python tools read the same mapping while the game runs.

## Detection and the wait logic

- **Single notes:** onset detection + YIN pitch on the tap audio ([detector.cpp](../mod/nbn/detector.cpp)). 150 ms refractory, the same note is never reported twice within 120 ms (the attack through an ASIO interface rises over 30-70 ms).
- **Chords:** YIN can't follow a chord, so after each attack the spectrum is checked at +90 and +180 ms (4096-sample Hann window, zero-padded to 16384). Notes are picked one by one by harmonic sum over *unexplained* peaks only, a candidate needs its own fundamental, and the result is compared by pitch class (strongest note + all classes, or all but one for big chords, and no strong wrong class). Tested on 696 synthetic strums (3 fails).
- **When the song stops:** when the song clock reaches the next waitable note (minus an optional lead) and it wasn't heard. A note played up to `EarlyMs` (300 ms) early counts. For a chord, if a strum is still being checked, the stop waits up to 200 ms past the note, so a chord played on time doesn't stop the song.
- **Timing notes:** the WAIT log line says how far past the note the song stopped ("stopped at +N ms"): single notes stop 0-8 ms late, chords up to ~60 ms with a guitar plugged in. A failed freeze (e.g. no music yet) is retried after 0.5 s; an earlier version also waited after *successful* freezes, which made stops on fast passages up to 0.35 s late.

## Overlay

- **Hooks:** a throw-away D3D9 device gives the addresses of `Present` (vtable 17) and `Reset` (16) in d3d9.dll; both are hooked with MinHook (hooking system DLLs is fine; only the game's code is protected). Present, not EndScene: once per frame; the back buffer is set as render target, ImGui draws, the old target is restored. Reset releases and recreates ImGui's device objects.
- **Window:** the device's focus window is an **ANSI** window: subclass it with `SetWindowLongPtrA` / `CallWindowProcA`. While our menu is open, keyboard, mouse and `WM_INPUT` go to ImGui and are hidden from the game; ImGui draws its own cursor (`ImGuiConfigFlags_NoMouseCursorChange`).
- **Unload:** the render thread frees ImGui on its next frame, then the hooks are removed after an in-flight counter drops to zero.
- **Scale:** everything is laid out in 1080p pixels times screen height / 1080, like the game's own UI.
- **The tab** (DrawTab): time runs left to right at one speed for the whole tab, so gaps are rhythm. Fast passages zoom smoothly (and first shrink the numbers a little); a fast repeat of one fret is drawn once as `12 x8`. Page mode keeps notes still under a moving cursor; with 2-4 rows the next pages wait in the rows below, each starting with a dimmed repeat of the end of the page before, and while the cursor is in that repeated part a dimmed copy of it shows on the next row. The cursor never passes the next note the song would stop at, so it doesn't jump back when a stop lands a few ms late. Bar lines and rhythm (stems and beams) come from the beat vector above.
- **Themes:** all overlay colours except the string colours come from a theme ([theme.h](../mod/nbn/theme.h)); the string colours stay the game's, because the text names them ("the ORANGE string").

## Start-up helpers

- **Screen names** (from the menu chains) seen at start-up: `MainOverlay` → `TitleScreen` → `UplayLoginDialog` → `SelectionListDialog` → `ProfileSelect` → `SimpleDialog` (autosave notice) → `MainMenu`. [startup.cpp](../mod/nbn/startup.cpp) answers the two Ubisoft dialogs by posting `WM_KEYDOWN`/`WM_KEYUP` (Esc) to the game window; it acts only on those screens, only before the main menu, and stops at the first screen it doesn't expect.
- **Faster logos:** the intro is a Scaleform movie with fixed timing that keys don't skip. [fastintro.cpp](../mod/nbn/fastintro.cpp) hooks `ntdll!RtlQueryPerformanceCounter` and `winmm!timeGetTime` so the clocks run N times faster until the title screen, then continue at normal speed from the fake time (a clock never goes back). The game reads QPC ~75,000 times during the intro. Title after ~7 s instead of ~26 s, loading keeps up. No game files are changed.

## The game's own random crash

Not caused by any mod, but found while testing. VMProtect replaces the first instruction of `ntdll!NtProtectVirtualMemory` with a `jmp` to a trampoline page (`mov eax,50h; jmp ntdll+5`, then `jmp [..]` into the exe's `.UBX0` section). That handler sometimes "returns" to a garbage address, a different one each time, most likely a race between threads. Every game crash dump examined (heap allocation → VirtualProtect → NtProtectVirtualMemory → handler → garbage) and one hang (while the loader lock was held during a FreeLibrary) show exactly this.

[crashfix.cpp](../mod/nbn/crashfix.cpp) puts ntdll's original first instruction back:

1. Only if the function starts with a `jmp`.
2. The original bytes come from ntdll.dll **on disk** (SysWOW64 for a 32-bit process), with the rest of the function required to match memory.
3. The page is unprotected through the stub itself (`mov eax,n; jmp fn+5`, straight to Windows, not the handler).
4. The 5 bytes are written with one `InterlockedCompareExchange64` (the function is 16-byte aligned), then the protection is restored and the instruction cache flushed.

A heartbeat re-checks every 5 s and repairs it again if the protector puts it back. 6 unattended full starts afterwards: no crash. The game runs normally without the handler.

## Pitfalls and tools

- **The exe is encrypted on disk** (`.text` looks random; `.UBX0` is the protector), so the file can't be studied as it is. Study the game's code **in memory while it runs** instead (address = base + RVA). [capstone](https://www.capstone-engine.org/) from Python was enough; no Ghidra needed.
- **`VirtualProtect` on the game's code returns ACCESS_DENIED** (the redirected NtProtectVirtualMemory). So no inline hooks in the game's code; RSMods uses a direct syscall for its hooks.
- **Hardware breakpoints work** and VMProtect doesn't react: DR0-DR3/DR7 on all threads + a vectored exception handler give "who writes/reads this address" and execution breakpoints that log a function's arguments without changing code. That's how the clock, the DD state and the note search were found.
- **Keys to avoid** for test hotkeys: F10 (the Windows menu-bar key freezes rendering), F11 (white flash), F12 (Steam screenshot), Ctrl+number (game shortcuts).
- `small` is a macro in the Windows headers (rpcndr.h): don't name a variable `small`.
- Reading game memory from **outside** (OpenProcess + ReadProcessMemory, [tools/memread.py](../tools/memread.py)) is the quickest way to explore data; nothing is injected.

## Working with RSMods

Note-by-Note is a separate DLL today, but most of it could live inside RSMods. What it would need from the framework, in rough order:

1. **Per-frame drawing** in the overlay (free ImGui draw calls every frame) and the mouse for the overlay's drag-to-arrange mode; an out-of-tree mod route and a licence.
2. **Raw guitar audio**: RS_ASIO patch as today, or a WASAPI/ASIO capture hook inside RSMods.
3. An exclusive **song pause/resume** primitive (the freeze above), restored if the mod unloads.
4. **Readers**: song object + real clock (`song+0x3B4`), the arrangement in memory (`song+0x78`), DD state (`song+0x7C`), clock provider (vtable, `+0xCC`, `+0xDA`), and a "chart ready" event.
5. Nice to have: the start-up dialog names and early clock hooks (fast intro), the crash fix.

All the data above is free to use; if you use it in RSMods or elsewhere, a mention of Note-by-Note is appreciated. Questions and corrections: open an issue.
